### 第 3 層: 代碼優化 (2026-03-07 08:45-08:50)

**優化 1: 智能初始化等待**

```python
# 位置: offline_local_chat.py 行 161-195
# 改進: check_ollama_health(wait_timeout=30)

改進前:
  def check_ollama_health():
      try:
          resp = session.get(self.ollama_check_url, timeout=15)
          if resp.status_code == 200:
              return True
      except:
          return False
      # ❌ 立即返回，不等待

改進後:
  def check_ollama_health(wait_timeout=30):
      start_time = time.time()
      while time.time() - start_time < wait_timeout:
          try:
              resp = session.get(self.ollama_check_url, timeout=15)
              if resp.status_code == 200:
                  # ✅ 驗證模型加載
                  names = [m['name'] for m in resp.json().get('models', [])]
                  if names:
                      return True
          except Exception as e:
              elapsed = time.time() - start_time
              if elapsed < 5:
                  self.log(f"🔄 初始化中 ({int(elapsed)}s)...", "DEBUG")
              else:
                  self.log(f"⏳ 初始化中 ({int(elapsed)}s)...", "WARN")
          time.sleep(1)
      return False
```

**效果**:

- ✅ 系統啟動時主動等待 Ollama 完全初始化
- ✅ 而不是立即返回「失敗」

**優化 2: 改進的錯誤恢復**

```python
# 位置: offline_local_chat.py 行 197-270
# 改進: 區分 500 錯誤原因並自動調整

改進前:
  for attempt in range(3):
      response = session.post(...)
      if response.status_code == 200:
          # 成功
      elif response.status_code == 500:
          # ❌ 立即嘗試切換模型或放棄

改進後:
  consecutive_500_errors = 0
  for attempt in range(3):
      response = session.post(...)
      if response.status_code == 500:
          consecutive_500_errors += 1
          # ✅ 追蹤連續 500 個錯誤
          if consecutive_500_errors > 1:
              # ✅ 連續多次說明是初始化延遲，給更多時間
              self.log("💡 Ollama 可能正在初始化，等待 5 秒...")
              time.sleep(5)
```

**效果**:

- ✅ 自動檢測暫時失敗 (初始化中) vs 永久失敗
- ✅ 避免不必要的重試或模型切換
- ✅ 增加成功概率

## 💡 關鍵洞察

### 為什麼之前失敗?

1. **根本原因**: Ollama 重啟序列需要 10-15 秒
   - `/api/tags` 在 1-2 秒時就緒 ✓
   - `/api/chat` 在 10-13 秒時就緒 ✓
   - 期間 `/api/chat` 返回 500 ✗

2. **症狀被誤解**:
   - 用戶以為是超時不足 (120s 實際充足)
   - 實際是服務暫時不可用 (500 錯誤)
   - 重試策略無法區分原因

3. **解決思路**:
   - 而不是盲目重試，應該等待
   - 而不是增加超時，應該智能初始化檢查
   - 而不是忽視 500，應該自動調整等待時間

### 為什麼改進有效?

1. **智能等待**: 系統啟動時已經知道何時可以進行查詢
2. **自適應重試**: 500 錯誤時自動增加等待，不浪費時間
3. **清晰日誌**: 用戶能理解系統在做什麼，而不是「卡住了」
